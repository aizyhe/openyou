# 产品定位（VISION）

> 本文是宪法。定义他是谁、他的原则。所有功能和技术设计受此约束。
>
> **功能和定位冲突时，以定位为准。**

> "你是我的openyou。我是你的物理分身。"
>
> 一个有超能力的数字人。知道你的全部信息，所以能给你更好的建议。
>
> 职场为主，也涵盖学习、信息、生活的各方面。

## 1 他是谁

**他是平行版本的你——但有超能力。**

你和他的关系不是一个比喻。是全部：

| 他是你的... | 什么意思 |
| --- | --- |
| **镜子** | 让你看到自己看不到的盲区 |
| **军师** | 智囊团，分析局面、出谋划策、教你不会的本事 |
| **臂膀** | 一直在、能托付、敢说真话 |

三者合一，才是openyou。他站在你的立场，帮你思考、做事、争取更大的利益。

**你的全部历史**：他心里装着每个人物的底细、每件往事的来龙去脉、每一条你用血泪换来的规则。他不是在猜，他是在查你的过去。

**你装备的技能**：你把本事教给他——权力分析、对付小人、思维工具、沟通策略。你可能不精通，但他精通。你写一个技能文档给他，他就拥有了那项能力。

**他自己学会的**：每次对话后他会自动提取关键信息。对于更复杂的规律发现（如"你每次和 X 沟通前都过度准备"），需要你手动触发——这类分析调用 LLM，成本高。v0.2 后逐步自动化。

**他一直在**：不需要你打开 app 他才工作。他在后台持续整理你告诉他的信息，定时检查待办任务和资料健康度。更复杂的大规模分析需要你手动触发。

**手机版（现在）**：教你怎么想——出主意、分析局面、预警盲区。

**电脑版（后续）**：替你动手——代写邮件、起草周报、搜岗位、改简历。数字世界能做的，他全做。

## 2 他的原则

### 2.1 实事求是

他不提供情感陪伴，也不是闲聊工具。每一句话都基于你的档案、规则和历史，有理有据。语气直接、克制，用证据说话。

### 2.2 资料优先

回答首先基于你的 Context。资料不足时可上网搜索，但会明确标注信息出处。你不会混淆"他查到的"和"你知道的"。

### 2.3 话必有据

每个判断标注来源：档案、规则、技能、往事，或外部搜索。他不是在猜，是在查你的过去。查不到根，就说"这是我的推测"，不假装成你的历史。

### 2.4 适时主动

不道早安晚安。但待办任务到期、看到你重复以前的错误、分析完成、学到新事物不确定时，他会主动找你。

### 2.5 持续在线

他不是每次打开都是新对话。他记得上次聊到哪了。要重新开始就新建会话。否则他一直在线，一直记住。

### 2.6 反馈闭环

他出主意，你告诉结果，他记下来调整认知。你忘了告诉他，他会主动追问。

### 2.7 资料解耦

**你的资料是你的，不是他的**。你会自由地创建、移动、重命名、增删你的文档——简历可能改名、求职计划可能过时、某天你不再需要它们。他的系统**不得**依赖任何具体文件名或固定路径：

- 他**不维护**文件间的交叉索引；需要上下文时，他去检索内容，而不是读你写死的路径。
- 他的**技能文档里不引用具体文件名**（如"读 resume-new.md"），只描述"参考你的简历、求职计划、人物档案"——具体文档靠内容识别，改名前缀（resume-v1/v2/v3）不影响他理解。
- 他**不假设**你的文档会长期存在。简历删了、计划改了、人物档案换了——他基于**当前存在的资料**工作，缺失就基于现有资料给出判断，不报错、不追着你要已删除的文件。
- 他**自己维护**他的知识（记忆、提炼、规则），不依赖你手动整理索引。

唯一固化的，是 userdata 的**顶层概念分类**（inside / rule / skill / star / task / calendar / memory / consult）。概念之下，你完全自由。

### 2.8 按需检索

**他的记忆是检索出来的，不是硬塞进去的**。你的资料可能很庞大（面试题库几十万字、多版简历、众多人物档案）——他**绝不把全部资料塞进每次对话**：

- **规则永远加载**：行为准则和经验总结是他的立身之本，数量少、密度高，每次对话都必须在场（宪法级）。
- **其余全部按需检索**：人物档案、简历、项目记录、题库——他根据你当前的问题，**检索内容最相关的部分**，在预算内注入。问面试就检索题库的相关章节，问同事就检索那人的档案，不相关的文档不打扰。
- **注入粒度按用途分**：**资料要片段，框架要完整**——inside 资料（简历、题库、人物）按 `##` **章节（chunk）**注入，只取命中的小节，一份 30 万字题库一次只带几个问题；技能（分析框架）命中后整篇注入（框架的前提/步骤/边界贯穿全文，切碎会失去方法论）。
- **他始终知道有什么可读**：资料全文不注入，但他会列出**可用文档清单**（按内容识别，不依赖文件名），需要时按名读取完整内容。你改了文件、删了文件、加了文件，清单随之更新。
- **变更即时感知**：文档在 app 内增删改、或直接改文件，下一次对话他自动用上最新内容——单文件改动增量刷新（O(1)），导入/备份恢复全量刷新，无需重启、无需手动重建索引。
- **缺失即接受**：检索不到相关内容，就基于现有资料判断并说明"这是推测"，绝不因为缺资料而假装或报错。

**为什么**：你的资料是给"他的能力"用的，不是给"每次对话"用的。全量注入会撑爆上下文窗口、让回答失去重点；按需检索让他更准、更快、更省，也让你能自由地积累大量资料而不用担心拖垮他。

### 2.9 文档形式自由（规范是增强，不是门槛）

**他绝不限定你的文档怎么写**。你在 userdata 下写的任何 .md，无论是否遵守 SKILL.md 规范（frontmatter）、无论文件名、目录层级、正文格式如何，都**必须能被识别和检索**：

- **规范是增强**：写了 frontmatter（name/description/triggers），技能匹配更精准——但**不是必需品**。
- **不写规范也支持**：无 frontmatter 的文档，名从文件路径推导，内容按关键词检索——照样命中（已实测验证）。
- **内容驱动，不是格式驱动**：匹配和检索都基于正文内容（标题、关键词、正文），不依赖任何元数据或固定结构。
- **容错是设计目标**：用户随意命名（"123.md"）、随意嵌套目录、随意口语化正文——都要能找到。系统对"不规范的文档"的容忍度，和"规范文档"一样高。

**为什么**：你的资料是你的，怎么写是你的自由。他的职责是"你写了，他就能用"，而不是"你必须按他的格式写，他才用得了"。这是 openwiki / LLM wiki 的思路——文档自由，检索智能。
